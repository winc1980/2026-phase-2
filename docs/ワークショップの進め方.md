# このドキュメントについて

[環境構築.md](./環境構築.md)が終わっている前提で、Issueを1つ解いてPull Requestを出すまでの流れをまとめます。
Issueに取り組む際は、このドキュメントを見ながら進めてください。

# STEP.0 準備を確認する

以下のコマンドがすべて動くことを確認してください。

```sh
bun -v
```

```sh
gh --version
```

```sh
gh auth status
```

`gh auth status`が失敗する場合は、以下でログインしてください。

```sh
gh auth login
```

# STEP.1 取り組むIssueを選ぶ

Issueは、[環境構築.md](./環境構築.md)の`bun run setup`を実行した時点で、自分のリポジトリにすべて作成済みです。改めて何かを作成するコマンドを打つ必要はありません。

取り組む課題は、フォークしたリポジトリの「Issues」タブから確認できます。ブラウザで見てもいいですし、コマンドでも確認できます。

```sh
gh issue list
```

内容を詳しく見たいときは、番号を指定します。

```sh
gh issue view (issueの番号)
```

> [!note]
> Issueには`#1[Easy]...`のように番号と難易度が書かれています。まずは`Easy`から取り組むのがおすすめです。

# STEP.2 作業用ブランチを作る

`main`ブランチで直接作業せず、Issueごとに新しいブランチを作りましょう。

```sh
git checkout -b fix/env-gitignore
```

> [!note]
> なぜ`main`で直接作業しないのでしょうか？
> `main`はいつでも動く状態を保っておきたいブランチです。作業用のブランチを分けることで、途中の変更が`main`に混ざらず、失敗してもやり直しがききます。
> ブランチ名は自由ですが、何のIssueに対応するか分かる名前にしましょう。
> なお、`bun run setup`によって`main`ブランチにはPull Request必須のルールが設定されているため、`main`ブランチへ直接コミットしてpushすることはそもそもできません。

# STEP.3 開発サーバで確認しながら作業する

```sh
bun run dev
```

ターミナルに表示されるURLをブラウザで開き、実際の画面を見ながらコードを直しましょう。

> [!note]
> VSCodeの内部ブラウザではなく、Google Chromeを使用すると良いです。ターミナル上で`o`を入力して`enter`すると、Google Chromeで開けます。

# STEP.4 コードをチェックする

作業がひと段落したら、フォーマッター・リンター（Biome）を実行しましょう。`bun run check` / `bun run check:write`というコマンドを使います。

> [!note]
> これらのコマンドはIssue 4（フォーマッター・リンター導入）に取り組んで自分で`package.json`に追加するまでは存在しません。Issue 4より前に取り組んでいる場合は、代わりに次のコマンドを直接使ってください。
>
> ```sh
> bunx biome check .
> ```
>
> ```sh
> bunx biome check --write .
> ```

```sh
bun run check
```

指摘された問題のうち自動で直せるものは、以下で修正できます。

```sh
bun run check:write
```

# STEP.5 コミットする

変更をステージして、

```sh
git add .
```

コミットします。

```sh
git commit -m "fix: .envをgitの管理から外す"
```

> [!note]
> コミットメッセージは「何を」ではなく「なぜ」を書けると尚良いです。慣れないうちは「何をしたか」を日本語で簡潔に書くだけでも十分です。

# STEP.6 プッシュする

```sh
git push -u origin fix/env-gitignore
```

> [!note]
> `-u`を付けると、次回以降そのブランチでは`git push`だけで済むようになります。

# STEP.7 Pull Requestを作る

```sh
gh pr create
```

タイトルや説明を聞かれるので、何をしたIssueなのかが分かるように書きましょう。

> [!note]
> Pull Requestの説明文に`Closes #3`のように書いておくと、そのPull Requestがマージされたときに自動でIssue番号3が閉じられます。対応するIssue番号を確認して書いておきましょう。

作成されたPull RequestのURLが表示されるので、ブラウザで開いて内容を確認してみてください。

> [!note]
> `main`ブランチには、`bun run setup`で設定されたルールにより「1件以上のレビュー承認」と「コードオーナー（学習会メンター）によるレビュー」が必須になっています。Pull Requestを作成したら、メンターにレビューを依頼しましょう。

# STEP.8 次のIssueに取り組む

`main`に戻り、最新の状態を取り込んでから、STEP.2に戻って次のIssueに取り組みましょう。

```sh
git checkout main
```

```sh
git pull
```

# upstreamの更新を取り込みたいとき

学習の途中で新しいIssueが追加されたり、元のリポジトリ（`upstream`）に修正が入ったりすることがあります。取り込みたいときは、[環境構築.md](./環境構築.md)で実行した以下のコマンドを、いつでも再実行して構いません。

```sh
bun run setup
```

`upstream`の変更を`main`ブランチに取り込みつつ、ブランチ保護ルールやIssueの内容も最新の状態に更新してくれます。

# 困ったときは

## 変更を元に戻したい

まず今の状態を確認します。

```sh
git status
```

特定のファイルの変更だけを取り消したい場合は、

```sh
git restore (ファイルパス)
```

1つ前のブランチに戻りたい場合は、

```sh
git checkout -
```

> [!warning]
> `git reset --hard`のような、変更を完全に消してしまうコマンドはここでは使いません。
> 分からなくなったら、消す前にまず`git status`で状況を確認する癖をつけましょう。

---

進め方が分からなくなったら、遠慮せず講師・メンターに質問してください。
